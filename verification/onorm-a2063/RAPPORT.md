# ÖNORM A 2063 (.onlv / .onlb) — verification report

## Question and approach

Can Open Calc Studio read the Austrian exchange format ÖNORM A 2063 — a
Leistungsbuch (.onlb, the catalogue of standard texts) and a
Leistungsverzeichnis (.onlv, the priced or unpriced bill of quantities) —
and write an .onlv that other AVA software accepts, without silently losing
or inventing anything?

Three checks, all automated:

1. **Import of the real Leistungsbücher.** The five official/demo LBs
   (LB-Hochbau 023 and LB-Haustechnik 014 in both schema editions 2015 and
   2021, plus the small demo LB-SCHOKO) are imported and the result is
   counted against the raw XML: every `lg`/`ulg` must become a chapter,
   every `folgeposition`/`ungeteilteposition` a position (or a text row
   when it has no unit). The 2015 and 2021 editions of the same LB must
   import identically. Origin of the files: [README.md](README.md).
2. **Round trip.** A priced LV is built from an LB (deterministic
   pseudo-random quantities and Lohn/Sonstiges prices, one in ten
   positions an Eventualposition), exported as .onlv, imported again and
   compared row by row: row type, code, description, unit, quantity,
   labour price, material price, unit price, total, depth, parent, notes
   and the "verrekenbaar" flag. The OCS example estimate (with resource
   rows and overheads, which the format cannot carry) is exported and
   compared on positions and totals.
3. **Schema validation.** Every exported file is validated against the
   official `onlv.xsd` (2021-03-01) with `scripts/validate-a2063.py`
   (lxml/libxml2). To make sure "valid" means something, the validator is
   also run on the official LBs (must pass) and on a deliberately broken
   copy of LB-SCHOKO with the unit `zak`, which is not in `einheit.type`
   (must fail).

The block "Measurements" below is written by the test itself
(`npx vitest run src/test/onlvRoundtrip.test.ts`); the text after it is
written by hand.

| `grundtextnr` + `folgeposition[@ftnr][@mfv]` | Position (begrotingspost); code = full Positionsnummer `lg.ulg.gtnr` + `ftnr` + `mfv`, e.g. `01.02.03A` |
| `grundtextnr` + `ungeteilteposition[@mfv]` | Position; code `lg.ulg.gtnr` (+ `mfv`) |
| `gliederung-posfrei/position[@nr]` (LV without groups) | Position with the free number as code |
| `stichwort`, or `stichwort-kurz` + `stichwort-luecke` | Description |
| `grundtext/langtext` + position `langtext` | Notes, as plain text lines; the Grundtext comes first (it is the shared first half of every Folgeposition's text) |
| Formatted text (`p`, `br`, `b`, `i`, `u`, `sup`, `sub`, `tt`, `h1`–`h3`, `ul`/`ol`/`li`, `table`/`tr`/`td`) | Plain text: block elements become lines, `li` gets "- ", table cells are joined with " \| " |

| `nichtangeboten` (no price offered) | No price; if no position has a price the import warns that the file is unpriced |

## What is not imported

- **Mengenermittlung** (`berechnetemenge`, `mengenermittlung`, the
  per-Abrechnungskennzeichen quantities) — OCS has one quantity per
  position; only `lvmenge` is read.
- **Formulas** (`onformel.xsd`: Rechenwerte, Formeln, Bedingungen inside
  texts) — a `rw` element is rendered as its literal content.
- **Parameter lists** (`parameterliste`, pictograms), **graphics**
  (`grafiktabelle`, `grafiklinks`), and **`kommentar`** on positions.
- **Nachlässe/Aufschläge** (`nachlass`, `summe-inkl-na`,
  `zugelassenenachlaesse`), **USt** (`ustkennzeichen`, `ust`), price
  conversions and index definitions (`indexwarenkorb`, `festpreise` /
  `veraenderlichepreise` per Leistungsteil), `preisumrechnung`.
- **Leistungsteile** (`leistungsteil`), **Änderungskennzeichnungen**,
  `herkunftskennzeichen`, `zusatzangebot`, Bieter-specific data
  (`bieter`, `angebotsdaten`).
- The other document types of the A 2063 family — ONRE (Rechnung), ONPR
  (Preisspiegel), ONIX (Index), ONBGS/ONBAEK/ONBPEK/ONBPEL (Bauabrechnung
  and Preisermittlung) — have other root elements and are rejected with a
  clear message; only `onlv` and `onlb` are read.
- Per-og Ständige Vorbemerkungen beyond the first og (only the first
  becomes the schedule description).

## What the export writes

- `kostenschaetzungs-lv` when at least one position has a price (the only
  pre-tender LV type in which the schema allows prices and group sums);
  otherwise an `ausschreibungs-lv` with `nichtangeboten` on every
  position. Namespace 2021-03-01, `preisanteilmodell/preisanteile`
  (Lohn/Sonstiges), one Leistungsteil, `zugelassenenachlaesse` on sums
  and hierarchy levels.
- Chapters → `lg`/`ulg` (2 levels); with 3 or 4 levels `og` and `hg` are
  added in front; chapters deeper than 4 levels are flattened into their
  ulg with their heading as a wählbare Vorbemerkung. Loose positions get a
  synthetic ulg. Group numbers come from the last code segment (2
  characters), unique among siblings.
- Positions whose code ends in the ÖNORM pattern (`NN` + letter + optional
  Mehrfachverwendung) are written as `grundtext` + `folgeposition`;
  everything else as `ungeteilteposition`. `stichwort` and `ueberschrift`
  are cut at 60 characters (`text60.type`); a longer description goes in
  full as the first paragraph of the `langtext`. Notes become `langtext`
  paragraphs.
- Price per unit = Lohn (labour) + Sonstiges (everything else), 2 decimals.
  Resource rows (rekenregels) under a position are folded into that price;
  overhead rows (staart) are not exported — the recipient applies its own
  Nachlässe/Aufschläge. `pospreis`, `ulg-summe`, `lg-summe`, `lv-summe` and
  `summenormalausfuehrung` (with USt from the staart's VAT row, else 20 %)
  are written consistently with what the importer recomputes.
- "Verrekenbaar" = N (or the importer's Eventual/Wahl marker in the notes)
  → `eventualposition`, excluded from the sums.

## Round-trip results

- `lb-schoko-lv.onlv` (5 positions from the demo LB) and
  `lb-hb-deel-lv.onlv` (1,260 positions plus the wählbare Vorbemerkungen
  of LG 00 as text rows, from LG 00–03 of LB-HB-023-2021; 126 positions
  are Eventualpositionen and one unit has no OCS equivalent): **0 rows
  differ** on all 13 compared fields; direct cost identical
  to the cent; both files valid against `onlv.xsd`. Kenndaten (project,
  LV code, client, Ständige Vorbemerkung) come back unchanged.
- `voorbeeld.onlv` (the OCS example estimate: 6 positions with 9 resource
  rows and 10 overhead rows): every position comes back with the same
  description, unit and quantity; the direct cost differs by **−0.22**,
  which is entirely the rounding of three computed unit prices to 2
  decimals — see the table in the measurements block. The composition
  (resource rows) and the overheads are not in the file, as documented
  above; the export warns about both.
- Structure that changes by design after a round trip: a position's
  `Wesentliche Position (W)` note line and the Grundtext become plain
  `langtext` (a second import does not recognise them as such); a
  Wahlposition comes back as Eventualposition (both are "not counted",
  the exporter only writes `eventualposition`); og/hg chapter notes end up
  as the Ständige Vorbemerkung of the og (a hg has no place for notes at
  all — the export warns).

### The −0.22 on the example estimate, exactly

`betrag.type` in `ontypdef.xsd` is `xs:decimal` with `fractionDigits="2"`
(`totalDigits="12"`), and `preis/preisanteil1`, `preis/preisanteil2`,
`preis/gesamt` and `pospreis` are all of that type; `lvmenge.type` also has
2 decimals. A position with resource rows has a computed unit price
total ÷ quantity that generally has more decimals (2,280 ÷ 92 =
24.782608…). The schema leaves no room to write it more precisely, and
writing a "corrected" quantity would falsify the quantity. The effect per
position is quantity × (rounded − exact); the test computes that sum and
asserts that direct cost B − A equals it to the cent. It is therefore a
known, explained, bounded deviation (at most 0.005 × quantity per
position), not an unexplained loss. Positions whose price already has 2
decimals (every position without resource rows, and every position of the
LB-based LVs) come back exactly.

## Schema validation results

- All three exported files: valid against `onlv.xsd` 2021-03-01, 0 errors.
- Positive control: `LB-SCHOKO_V2021.onlb` and `LB-HB-023-2021.onlb` are
  valid against `onlb.xsd`.
- Negative control: LB-SCHOKO with `<einheit>zak</einheit>` is rejected
  with an error naming `einheit` — the validator does see errors.

## Bugs found during this verification

1. **Import too slow on the real Leistungsbücher.** With `DOMParser` and
   DOM traversal (`children`, `textContent`, `getElementsByTagName` per
   text) importing LB-HB-023-2021 (9.1 MiB, 231,780 elements) took
   2.2–2.6 s on its own and 8.4 s inside the full test suite (parallel
   workers), against a requirement of < 5 s; in the browser the DOM would
   also hold the whole 10 MB tree. The importer now reads the file with a
   small dedicated XML parser (`src/services/importers/liteXml.ts`) into a
   flat tree: 0.17–0.32 s per LB on its own (0.5–0.65 s inside the
   parallel test suite), of which 75 ms parsing. The parser was
   checked against `DOMParser` on all five LBs, on our own export and on a
   fragment with CDATA, comments, DOCTYPE, numeric and named entities,
   namespace prefixes and CRLF — 950,686 elements, identical names,
   attributes and text; malformed input (unclosed or mismatched tags,
   unknown entities, text outside the root) raises `XML parse error`.
2. **Wrong counts in the first draft of the README**: 438 lg / 1,104 ulg
   for LB-HB were counts of `<lg>`/`<ulg>` *references* inside
   `aenderungskennzeichnungen`; the real numbers (elements with a `nr`) are
   59 and 725, and the importer's chapter count matches them.
3. **Test coupled to the issuer name** — the practice test now compares the
   author with the file itself instead of a hard-coded string.

## Deliberately not done

- Importing Mengenermittlung, formulas, parameter lists, graphics,
  Nachlässe and USt details, Leistungsteile — see "What is not imported".
  OCS has no place for them; carrying them as notes would only bloat the
  estimate.
- Writing resource rows into the file. A 2063 has no per-position
  composition (the Preisanteile Lohn/Sonstiges are the only split), so
  the fold into the unit price is the correct mapping, not a shortcut.
- Writing `entwurfs-lv`/`angebots-lv`/`vertrags-lv` variants or Bieter
  data; the two LV types written cover "estimate with prices" and "bill
  to be priced".
- Distinguishing Wahl- from Eventualpositionen on export (OCS has one
  "not counted" flag).
- Testing against a priced .onlv from another program — none is
  publicly available.

## Verdict

- **Import**: works on all five official/demo Leistungsbücher in both
  schema editions, with identical results for 2015 and 2021, all groups
  and positions accounted for, and the only units without an OCS
  equivalent (`VE`, `l`) reported rather than dropped. 0.2–0.3 s per
  10 MB file.
- **Export**: schema-valid `kostenschaetzungs-lv`/`ausschreibungs-lv`
  files; a round trip of an LV built from an LB is lossless on every
  compared field, including Eventualpositionen, text rows, gaps and
  Lohn/Sonstiges prices.
- **Limits**: an OCS estimate with resource rows loses its composition
  and overheads in the file (the format has no place for them) and its
  totals shift by the 2-decimal rounding of computed unit prices — both
  reported to the user at export time and quantified here.
